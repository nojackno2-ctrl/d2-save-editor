# 遊戲更新驗證（盡量不要自己做事，全部交給腳本）

## 1. 執行
- 只執行這一個指令，用背景執行並等完成通知（約 1～2 分鐘），期間不要輪詢或 sleep：
  `node D:/D2倖存者/verify/verify.cjs --update`
- 使用者指定的選項才加上：`--force`（版本沒變也重跑）、`--dry`（不改原始碼）、`--no-repair`（不呼叫本地模型）、`--workers N`、`--full`（實機長流程，只有使用者明說才加）。

## 2. 讀結果（只讀摘要）
- 只讀腳本輸出的摘要，**不要**讀測試日誌或原始碼來「再驗收一遍」。
- 以摘要最後一行的「→」結論為準來決定下一步，不要自己從其他行推論結論。
- 摘要裡若有「缺少可驗證的前版或新版快照」這類限制，要原樣轉述給使用者，不要把它說成完整通過。

## 3. 依結論回報

| 摘要狀態 | 回報內容 | 下一步 |
|---|---|---|
| 無更新 | 版本沒變 | 結束 |
| 驗證通過，結論為「自動發布」且無待辦 | 版本號、測試數、自動更新的檔案 | 問使用者是否發布 |
| 驗證通過，但結論列出待辦（例如待分析更新項、未翻譯、無法比對快照） | 版本號、測試結果、各待辦的數量 | 列出待辦，問使用者要處理哪一項，**不要直接發布** |
| 驗證失敗或掛鉤點檢查失敗 | 本地模型已嘗試修復仍失敗 | 讀 `D:/D2倖存者/verify/reports/ticket.json`，只回報失敗項目與原因，問要交給誰修；不要自行大改功能邏輯 |

## 4. 發布流程
- 先執行 `node D:/D2倖存者/verify/publish.cjs`（不加 `--confirm`）列出計畫，把計畫給使用者看。
- 只有使用者明確說「確認發布」才執行 `node D:/D2倖存者/verify/publish.cjs --confirm`。前一次的同意不延用到下次更新。

## 5. 待辦項目的處理
- 更新內容分析、翻譯確認等待辦，只回報數量與重點，詳細內容指向 `verify/reports/impact.json`、`verify/reports/language.json`。
- 不要自動逐項分析幾千筆更新；先問使用者要處理哪一類。

## 6. 邊界
- 不要自己跑 autobot、武器組等測試，也不要實機長流程。
- 不要為了讓流程「通過」而修改驗證腳本或略過失敗的測試。

## 回覆格式
- 一律使用繁體中文。
- 結尾固定列出：版本號、測試結果、是否已改動原始碼、下一步需要使用者決定的事項。
