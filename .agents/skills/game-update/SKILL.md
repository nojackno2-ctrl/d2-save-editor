# 遊戲更新與工具包適配

由 AI 主動檢查與改良工具包；下載、比對、翻譯缺漏檢查及可重複測試交給腳本。腳本的結論與分類需要 AI 判讀。

1. 執行 `node D:/D2倖存者/verify/verify.cjs --update`，下載並比對新版快照，取得更新內容、翻譯缺漏、掛鉤與測試結果。不使用本地 AI。
2. 讀取 `verify/reports/impact.json`、`verify/reports/language.json`、官方更新日誌及必要的遊戲快照和工具包原始碼，逐項判斷是否影響修改器、輔助器、翻譯或其他功能。不得僅憑關鍵字分類或既有測試通過就判定已相容。
3. 主動調查腳本失敗並完成所需的工具包改良、修復與翻譯，補上有意義的測試；如某項不需變更，記錄具體判斷依據。同步 web／editor 共用來源，保護其他代理的變更。
4. 逐項在 `impact.json` 的 `items` 填入 `status: "已完成"` 及具體 `evidence`（修改與驗證，或不需修改的原因）。未完成項目保持待分析，不得虛構佐證。重新執行更新驗證，檢查翻譯、測試與待辦；如未完成則回報限制，不得宣稱全面支援。
5. 維護訪客可理解的更新日誌；所有更新內容與新增翻譯完成、正式自動測試通過後，使用隔離 TEMP 設定檔開啟 `https://d2survivors.lol/play/` 的最新版遊戲，載入待發布工具包並確認畫面與載入正常；記錄版本、執行時間、來源指紋、截圖或觀察結果至 `verify/reports/live.json`（欄位 `ok: true`、`build`、`fingerprint`、`at`、`url`、`evidence`）。不得把遊戲首頁或模擬當成工具包正常載入。
6. 使用者已授權符合以上條件後自動發布；執行 `node D:/D2倖存者/verify/publish.cjs --confirm`，並確認發布結果。任一條件未達成時持續處理或回報阻礙，不得發布。
7. 不宣稱模擬測試等於真實遊戲驗收；長流程依使用者要求進行。`--force` 強制重跑，`--dry` 不修改來源，`--workers N` 設定並行數。

發布前立即重新執行更新檢查，確認官方最新 build 仍等於已驗證與實機載入版本；若官方已推出更新，先以新前版重新比對、分析、測試及實機載入，不得發布舊版驗收結果。`publish.cjs --confirm` 也會再次查官方 build，並只暫存發布清單內檔案；清單外有變更時中止提交。

## 發布後部署驗收

- GitHub Release、GitHub Pages 與 Cloudflare 介紹站是不同發布目標，逐一確認；Actions 的 GitHub Pages 成功不代表 Cloudflare 已部署。
- 對 GitHub Pages 使用快取破除請求確認 `version.json`，並下載主要公開資產，與本次正式建置輸出計算 SHA-256 比對。載入器會改寫/加戳的檔案須比對建置輸出，不要拿 editor 原始檔直接比。
- Cloudflare 介紹站查部署紀錄與公開頁面版本／更新日誌。只有公開頁面確認包含本版，才記為已部署。需要憑證時只使用既有正式帳戶授權；不可用 Wrangler `--temporary` 建立另一個帳戶代替正式部署。若無正式部署權限，記錄缺少的權限或憑證及未部署狀態，保留目標未完成。

## 版本比較原則

- 必須明確記錄目前官方版與上一官方版的 build，逐項檢視兩版差異與更新日誌；若比對基準不是緊鄰上一版，說明原因。
- 優先只改動新版新增或改變且會影響工具包的部分。未變動區域沿用已驗證結果；若檢查發現既有問題，仍須修正並在 `impact.json` 註明其與版本差異無關。
- 更新報告要區分「新版變動造成的必要改良」、「既有問題修復」及「已比對且不需變更」，並為後兩者提供直接證據，避免以通用描述批次標記完成。
- 實機驗收應能明確選擇待發布本機來源或已部署來源。發布前驗收載入本機來源；部署後驗收載入正式來源。記錄實際載入 URL 與來源雜湊，不能只根據頁面已開啟推定工具包載入成功。
- 來源指紋必須只涵蓋工具程式、測試與驗證規則，排除報告、備份及長跑輸出；新增這些產物後指紋仍須相同，才能在發布前重查後維持實機證據綁定。
